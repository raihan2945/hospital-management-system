Project Overview

Layered web application
Controller → Service → Repository → Database

A single web application that replaces a hospital's paper registers. Staff register patients and doctors, book conflict-free appointments, issue invoices, record payments, and watch live totals on a dashboard — all backed by a PostgreSQL database and protected by validation at every layer.

The problem

Paper records are slow to search, easy to lose, and let two patients be booked into the same doctor's slot.

Our solution

One browser-based system where every record is searchable, every rule is enforced by the server, and money is never miscalculated.

How it is built

Object-oriented Java with a clean layered architecture, so each module can grow without breaking the others.

Features

Beyond the Basics

The engineering that makes it
safe to use for real work

No double booking

Booking locks the patient row and then the doctor row in the database, so two staff members clicking “Save” in the same second can never reserve one slot twice.

No duplicate payments

Each invoice carries a version number. A stale or resubmitted payment form is rejected with a clear “reload and check history” message instead of charging twice.

Validation everywhere

Bean Validation runs in the browser, in the controller and again at the service boundary. Invalid forms keep what the user typed and move focus to the error.

Safe error handling

Friendly 400 / 404 / 405 / 409 / 503 pages. Raw SQL, stack traces and rejected values are never shown to the user; a support reference links to the log.

Responsive, accessible UI

Shared navigation with a mobile off-canvas menu, keyboard focus outlines and confirmation dialogs — and every page still works with JavaScript switched off.

Presentation-ready demo data

One switch seeds 5 doctors, 10 patients, 10 appointments, 5 bills and 4 payments through the real services — and never touches a database that already holds records.

Object-oriented design

The Four Pillars in Our Code

Not theory — each pillar points
at a real class in the project
1

Encapsulation

Every entity field is private. State changes only through guarded methods such as rename() and applyPayment(), which validate before assigning. IDs and audit timestamps have no setters at all.

2

Inheritance

Patient and Doctor extend Person, which extends BaseEntity. Name, contact, ID and timestamp behaviour is written once and reused by all six entities.

3

Polymorphism

Four PaymentProcessor implementations are injected together. The billing service calls process() without knowing whether the money arrived as cash, card, mobile banking or bank transfer.

4

Abstraction

BillingCalculator and PaymentProcessor are interfaces; BaseEntity and Person are abstract. Services depend on the contract, never on a concrete class.

The payoff

Adding a fifth payment method means writing one new class that implements PaymentProcessor — no existing service, controller or template has to change. That is the Open/Closed principle in practice.
